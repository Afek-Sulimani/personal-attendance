# Company Registration

**Status:** Implemented for the local assignment environment.

## User flow

1. A company representative opens `/register-company`.
2. The representative enters the company name and the first representative's name and email.
3. The API creates an active company, assigns a generated five-digit company code, and creates a 48-hour invitation in one SQL transaction. The first representative receives the `Admin` role only.
4. The result page shows the company ID, contact email, a short account-activation label, a Copy button, and `The activation link expires 48 hours.` The Copy button copies the full URL; the URL and token are not shown as text. No email is sent.
5. The representative passes the copied link to the employee. The employee opens `/activate`, chooses a password, and accepts the invitation.
6. Invitation acceptance creates the Identity account, company membership, employee profile, and Admin role.
7. The new Admin signs in with the generated company ID or exact company name, invited email, and new password. Admin then completes company payroll settings and can invite Payroll, HR, managers, and employees.

## API contract

### `POST /api/companies/registration`

The endpoint is public in the local assignment configuration and requires the antiforgery header used by the React API client.

Request body:

```json
{
  "companyName": "Example Company",
  "companyRepresentativeName": "Alex Example",
  "companyRepresentativeEmail": "representative@example.com"
}
```

The server returns `201 Created` with the generated `companyCode`, the representative details, and an activation URL. Invalid input returns `400`; a persistence conflict returns `409`; database unavailability returns `503`.

## Data and security

- The company code is generated by the server as five decimal digits, with no prefix. The server checks for existing codes and retries a uniqueness collision up to five times.
- The company and its first invitation are saved in one transaction so a failed registration does not leave an orphan company.
- The first invitation has the `Admin` role and no manager membership. It does not create Payroll settings; an Admin or Payroll representative must explicitly configure them after activation.
- The Admin setup migration upgrades accepted first-representative invitations created under the former HR + Payroll rule when their membership still has exactly those two roles. Existing login sessions must sign in again to receive refreshed role claims.
- `CreatedByMembershipId` is nullable because public company registration has no existing company member who could be its creator.
- The activation token is random; only its SHA-256 hash is stored. The raw token is returned only inside the activation URL, which is copied by the representative and passed to the employee.
- The invitation expires 48 hours after creation and can be accepted only once. The registration API does not return an exact expiry timestamp.
- The activation link is delivered manually because no email service is configured. The application does not independently verify mailbox ownership; the representative is responsible for giving the link to the intended person.

## Production boundary

Public company creation is intended for the local assignment flow. A production deployment should accept a company-creation request and require system representative approval before activating the company and issuing the first company representative invitation. Production role assignment must be reviewed separately.

## Database migration

Migration `20261120061729_CompanySelfRegistration` changes `CreatedByMembershipId` to nullable. Apply the migration before using the registration endpoint against an existing SQL Server database.
